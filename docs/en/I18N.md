# Localization guide

The application ships with the registered locales listed in
`frontend/src/locales/registry.json`. English (`en`) is the source catalog and
fallback. Users choose the interface language in **Settings**;
the change applies immediately and is saved in the existing application config.

## Frontend messages

Catalogs are nested JSON files in `frontend/src/locales/`, one per registered
locale. Keep the same keys in every completed catalog. Use stable, lowercase,
dot-separated keys grouped by feature and message purpose, for example
`nav.library`, `settings.language.label`, `api.errors.file_not_found`,
`jobs.download.progress`, and `diagnostics.lint.missing_title`. Frontend code
must use statically typed `t()` keys; update every supported catalog in the
same change.

Use ICU message syntax for interpolation and grammatical forms. For example:

```json
{
  "cover_alt": "Cover: {title}",
  "track_count": "{count, plural, one {# track} other {# tracks}}"
}
```

Use named placeholders such as `{title}` and preserve the same argument names
and ICU argument kinds in every locale. For English plural messages provide
`one` and `other`; for Russian provide `one`, `few`, `many`, and `other` (exact
number selectors such as `=0` may also be used where appropriate). Use ICU
`select` for named variants, not hand-built language-specific string logic.

## Locale selection and fallback

To start a new translation, run:

```bash
python scripts/new_locale.py es --name "Español"
```

The command copies `en.json` to `es.json`, creates `es.todo.json` with every
source leaf key, and registers `es` immediately. Translate values in `es.json`
and remove completed keys from `es.todo.json`. Keys remaining in the TODO file
are omitted from the runtime Spanish catalog, so i18next renders their English
fallback. An empty TODO file means the locale is complete. Run
`python scripts/check_locales.py` to inspect catalog contracts and remaining
TODO keys.

The saved `language` setting in `GET/PUT /api/settings` is authoritative when
present: it is a code registered in `frontend/src/locales/registry.json`; an
unset or invalid saved value is represented as `null`. On startup, a supported cached browser choice is provisional while
settings load. Once settings load, a saved server language takes precedence. If
no choice is saved, a supported `navigator.language` value is used (`ru-RU`
resolves to `ru`, for example); otherwise English is selected. If the settings
request fails or times out, the provisional locale is preserved (from
`localStorage` or the browser-derived choice). English is also the `i18next`
fallback. A settings save failure does not revert the active language; the
application reports the error in that language. Language selection updates the
document's `lang` attribute.

Known structured messages resolve through the active catalog. In development
and tests, missing codes are reported visibly; the UI must not display an
opaque key. In production, a known-code miss uses a readable compatibility
message when supplied, otherwise the localized generic unavailable message.
Existing plain-string messages continue to display verbatim.

## Backend message descriptors

Backend-owned user messages use `message(code, params=None, *, fallback)` from
`src.messages` (also re-exported by `src.web.messages`). For example:

```python
message(
    "api.errors.file_not_found",
    {"path": path},
    fallback=f"File not found: {path}",
)
```

The JSON-compatible descriptor has the shape
`{"code": "…", "params": {…}, "message": "…"}`. Use a stable catalog code,
pass interpolation values separately in `params`, and always provide a
readable, nonblank English `fallback`. The `message` field is for compatibility
and logs, not the normal localized rendering path. Do not put arbitrary Python
objects in parameters or derive codes from translated prose.

Legacy plain strings remain supported for existing API errors, job records,
and unknown or unstructured third-party errors. Preserve those strings
verbatim; do not wrap provider, operating-system, or other external exception
text in a catalog code. Unknown structured codes use their readable `message`
fallback, or a localized generic unavailable message if no usable fallback is
present.

## Data that must remain untranslated

Translate application-owned interface copy, not music metadata or user/provider
data. Keep track, artist, album, playlist, and lyric text; file and library
paths; filenames; tag values; provider labels and responses; browser/account
names; and technical identifiers unchanged. Pass such values as data or ICU
parameters when they appear in a localized sentence. Logs and non-user-facing
technical strings are not UI copy.

## Validation commands

Run these from the repository root when changing catalogs or user-facing copy:

```bash
python scripts/check_locales.py
python scripts/check_copy.py
cd frontend && npm run check:i18n-keys
```

The locale validator compares catalog structure and non-empty values, ICU
argument names and kinds, and required plural categories. The TypeScript check
enforces statically authored translation keys. `check_copy.py` is a scoped
heuristic: it examines selected JSX text/user-facing attributes and calls bound
to known notification/message constructors. It can miss copy outside those
patterns and is not proof that every source literal is localized. Historical
candidate scans have not been exhaustively reconciled line by line with the
current source, so a clean `check_copy.py` run means only that the current
checker found no candidates in its defined scope. Review its scope and any
reported candidate; distinguish actual UI copy from data, fixtures, provider
names, technical identifiers, and logs.

For broader verification, also run `pytest`, `cd frontend && npm test`, and
`cd frontend && npm run build` as appropriate to the change.
