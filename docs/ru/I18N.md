# Руководство по локализации

Приложение использует локали, зарегистрированные в
`frontend/src/locales/registry.json`. Английский (`en`) каталог — исходный и
используется как резервный. Пользователь выбирает язык
интерфейса в **Настройках**; переключение применяется сразу и сохраняется в
существующей конфигурации приложения.

## Строки интерфейса

Каталоги — вложенные JSON-файлы в `frontend/src/locales/`, по одному на каждую
зарегистрированную локаль. В завершённых каталогах должны быть одинаковые
ключи. Используйте стабильные
ключи в нижнем регистре, разделённые точками и сгруппированные по функции и
назначению строки, например `nav.library`, `settings.language.label`,
`api.errors.file_not_found`, `jobs.download.progress` и
`diagnostics.lint.missing_title`. В коде интерфейса используйте ключи `t()` с
проверкой типов. При изменении строки обновляйте все поддерживаемые каталоги в
том же изменении.

Для подстановок и грамматических форм используйте синтаксис ICU. Например:

```json
{
  "cover_alt": "Обложка: {title}",
  "track_count": "{count, plural, one {# трек} few {# трека} many {# треков} other {# трека}}"
}
```

Используйте именованные параметры, например `{title}`, и сохраняйте одинаковые
имена аргументов и типы ICU-аргументов во всех локалях. Для английского plural
укажите категории `one` и `other`; для русского — `one`, `few`, `many` и
`other` (при необходимости можно добавить точные селекторы, например `=0`).
Для именованных вариантов используйте ICU `select`, а не ручную сборку строк с
языкозависимой логикой.

## Выбор языка и резервный вариант

Чтобы начать перевод нового языка, выполните:

```bash
python scripts/new_locale.py es --name "Español"
```

Команда копирует `en.json` в `es.json`, создаёт `es.todo.json` со всеми
исходными ключами и сразу регистрирует `es`. Переводите значения в `es.json`,
а завершённые ключи удаляйте из `es.todo.json`. Ключи, оставшиеся в TODO,
исключаются из runtime-каталога, поэтому i18next показывает для них английский
fallback. Пустой TODO-файл означает, что локаль завершена. Для проверки
каталогов и оставшихся ключей выполните `python scripts/check_locales.py`.

Сохранённая настройка `language` в `GET/PUT /api/settings` имеет приоритет,
если она задана: её значение — код, зарегистрированный в
`frontend/src/locales/registry.json`; отсутствие или недопустимое значение
представляется как `null`. При запуске поддерживаемый язык из кэша
браузера используется временно, пока загружаются настройки. После загрузки
настроек сохранённый на сервере язык имеет приоритет. Если выбор не сохранён,
используется поддерживаемый `navigator.language` (например, `ru-RU`
определяется как `ru`), иначе выбирается английский. Если запрос настроек
завершается ошибкой или тайм-аутом, временная локаль сохраняется (из
`localStorage` или определяется по языку браузера). Английский также является
резервным языком `i18next`. Если не удалось сохранить выбор, активный язык не
меняется, а ошибка показывается на нём же. Атрибут `lang` документа обновляется
вместе с языком.

Известные структурированные сообщения отображаются через активный каталог. В
разработке и тестах о неизвестных ключах сообщается явно; интерфейс не должен
показывать непрозрачный ключ. В production при отсутствии перевода используется
читаемое совместимое сообщение, если оно передано, иначе — локализованное общее
сообщение о недоступной операции. Старые обычные строковые сообщения
по-прежнему отображаются без изменений.

## Дескрипторы сообщений backend

Для принадлежащих приложению сообщений пользователю используйте
`message(code, params=None, *, fallback)` из `src.messages` (модуль
`src.web.messages` также экспортирует эту функцию). Например:

```python
message(
    "api.errors.file_not_found",
    {"path": path},
    fallback=f"File not found: {path}",
)
```

JSON-совместимый дескриптор имеет вид
`{"code": "…", "params": {…}, "message": "…"}`. Указывайте стабильный ключ
каталога, передавайте значения подстановки отдельно в `params` и всегда задавайте
читаемый непустой английский `fallback`. Поле `message` предназначено для
совместимости и журналов, а не для обычного локализованного отображения. Не
передавайте в параметры произвольные объекты Python и не создавайте коды из
переведённого текста.

Старые обычные строки остаются допустимыми в существующих API-ошибках, записях
задач и неизвестных или неструктурированных ошибках сторонних сервисов.
Сохраняйте такие строки без изменений; не оборачивайте текст исключений
провайдеров, операционной системы и других внешних источников в ключи каталога.
Для неизвестного структурированного кода используется читаемое значение
`message`, а если его нет — локализованное общее сообщение о недоступной
операции.

## Данные, которые нельзя переводить

Переводите текст интерфейса приложения, но не музыкальные метаданные и данные
пользователей или провайдеров. Оставляйте без изменений названия треков,
исполнителей, альбомов и плейлистов, тексты песен, пути к файлам и библиотеке,
имена файлов, значения тегов, названия и ответы провайдеров, имена браузеров и
аккаунтов, а также технические идентификаторы. Если такие значения входят в
локализованное предложение, передавайте их как данные или параметры ICU. Журналы
и технические строки, не показываемые пользователю, не относятся к текстам UI.

## Команды проверки

При изменении каталогов или пользовательских текстов выполните команды из
корня репозитория:

```bash
python scripts/check_locales.py
python scripts/check_copy.py
cd frontend && npm run check:i18n-keys
```

Валидатор локалей сравнивает структуру каталогов и непустые значения, имена и
типы аргументов ICU, а также обязательные категории plural. Проверка TypeScript
контролирует статически заданные ключи переводов. `check_copy.py` — ограниченная
эвристическая проверка: она анализирует выбранные JSX-тексты и пользовательские
атрибуты, а также вызовы известных конструкторов уведомлений и сообщений,
связанные с нужными импортами. Она может не заметить строки за пределами этих
шаблонов и не доказывает, что каждый литерал в исходниках локализован.
Исторические списки кандидатов не были исчерпывающе сверены построчно с текущим
кодом, поэтому успешный `check_copy.py` означает только отсутствие найденных
кандидатов в пределах текущей области проверки. Учитывайте её границы и
проверяйте каждое предупреждение: это может быть UI-текст, данные, тестовый
пример, название провайдера, технический идентификатор или запись журнала.

Для более полной проверки также запускайте `pytest`, `cd frontend && npm test`
и `cd frontend && npm run build`, если это уместно для изменения.
